# Prior art: Cubby phase 3 authentication, center scoping, CSRF

Retrieved 2026-10-19. Research record for the phase 3 build.

## Decision first

- **Recommendation:** ADAPT the Rails 8.1 authentication generator shape (User with `has_secure_password`, database-backed `Session` rows, `authenticate_by`, `rate_limit`) instead of Devise or Rodauth. The web app uses the generator's signed httpOnly `SameSite=Lax` cookie. Mobile apps get an opaque bearer token on the same `Session` row, stored only as a SHA-256 digest. No JWT (D1, D2).
- **Evidence:** the installed generator's `authentication.rb.tt` and `sessions_controller.rb.tt` (E1). Community adaptations for API mode all add a token to the sessions table rather than JWT, because a database row can be revoked server side (E3, E4). Rails 8.2 moves CSRF protection to a `Sec-Fetch-Site` header check, with the header-only mode as the new default (E5, E6).
- **Limitation:** 8.1.4 does not ship the header strategy (E1, grep found no `Sec-Fetch-Site` in actionpack), so Cubby carries a small hand-written equivalent until an 8.2 upgrade. The exact 8.2 accept and reject rules were not read from source (E6 summary only).
- **Next check:** request specs proving one center's director gets 404 on another center's data at every endpoint (O1), and a cross-site cookie POST getting 403 (O3).

## Run header

- Outcome: authentication and tenancy foundation for the phase 3 director web app, compatible with phase 7 and 8 mobile clients. Mode greenfield. Profile Quick (4 searches/fetches, local generator read).
- Known constraints (E2): Rails 8.1.4 API-only app, React SPA served same origin in dev (Vite proxy) and in AWS (CloudFront path routing `/api/*` to the ALB), native iOS and Android clients later, fictional data, public repo.
- Local-first: read the installed railties 8.1.4 generator templates and actionpack 8.1.4 rate limiting and forgery protection (E1). No earlier auth record existed.

## Decisions

| ID | Decision | Status | Evidence | Recommendation |
| --- | --- | --- | --- | --- |
| D1 | Auth library / T1 | supported | E1, E3, E4 | Generator shape written by hand into the API app (no Devise, no Rodauth): `User`, `Session`, `Current`, `Authentication` concern; JSON responses instead of redirects |
| D2 | Credential type / T1 | supported | E1, E3, E4 | Web: signed httpOnly `SameSite=Lax` cookie holding the session id, `Secure` in production. Mobile: opaque 32-byte token returned once, stored as SHA-256 `token_digest` on the same `Session`; logout destroys the row. Sessions expire 30 days after creation |
| D3 | CSRF on cookie requests / T1 | supported | E5, E6, E7 | For unsafe methods authenticated by cookie (and for login itself): allow `Sec-Fetch-Site: same-origin`; if the header is absent, require `Origin` to equal `request.base_url` or an `APP_ORIGINS` entry; otherwise 403. Bearer requests are not checked, since browsers never attach them automatically. Replace with `protect_from_forgery` `:header_only` on 8.2 |
| D4 | Tenancy / T1 | supported | E2 | `memberships(user_id, center_id, role)` with a unique pair; `current_center = Current.user.centers.find(params[:center_id])`, so a foreign center is a 404, never a 403 that confirms it exists |
| D5 | Login throttling / T2 | supported | E1, E2 | `rate_limit` 10 per 3 minutes by IP and 5 per 3 minutes by normalized email on both login endpoints; test env switches to `:memory_store` so the limit is exercised |
| D6 | Edit conflicts / T2 | supported | E2 | Clients send `lock_version`; a stale value or a closed action returns 409 with the current row so the UI can refresh, reusing phase 2's guarded `transition!` |

## Limits

- E3 to E7 are search or fetch summaries, not verbatim reads. Rails 8.2's exact handling of `same-site` and `none` was not read from source; Cubby accepts only `same-origin`, which is stricter.
- No penetration test. The phase 6 deploy adds TLS, `Secure` cookies, and a real cache store for rate limits (memory store is per process).
- Review triggers: Rails 8.2 upgrade (switch to built-in header CSRF), adding a cross-origin client, adding parent (guardian) users in phase 7.
