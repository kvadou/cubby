# Prior art: Cubby phase 7 iOS parent app

Retrieved 2026-10-19. Research record for the phase 7 build.

## Decision first

- **Recommendation:**
  - Parents are users linked to one family through `guardianships`, scoped from `Current.user.families` the same way directors are scoped from their centers.
  - Approving a family-facing action writes a `family_messages` row in the same transaction, with a fixed subject.
  - A SwiftUI app (iOS 18+, Swift 6 strict concurrency, generated by XcodeGen) signs in with the existing bearer-token endpoint, keeps the token in the Keychain, and shows three tabs: Today, Messages, Billing (D1 to D6).
- **Evidence:**
  - Third-party listings of brightwheel's parent app describe a feed of updates, messaging, billing and mobile check-in (E1).
  - The phase 3 API already issues bearer tokens that are exempt from the same-origin check (E2).
  - The installed Xcode 27.1 toolchain builds the project, and runs it once CoreSimulator is updated (E3).
- **Limitation:** Simulator only; a device build needs Doug's Apple team. Daily reports and photos have no data model, so they're out of scope. Push notifications need an Apple developer account (stretch goal in the plan).
- **Next check:** O1 to O5 below.

## Run header

- **Outcome:** a parent app on the simulator against the local API, with a director's approval reaching the parent's inbox.
- **Mode:** greenfield. Profile Quick (1 search, local source, a live toolchain probe).
- **Known constraints:**
  - Phase 3 auth (bearer tokens, `Current.user` scoping).
  - The phase 2 rule that a director approves every family-facing message.
  - Fictional data.
  - Doug's native iOS design rules: semantic type and color, native List and TabView, 44 pt targets, Dynamic Type.
- **Local-first:** I read the cubby plan's mobile section, the phase 3 auth record, `ProposedAction#approve!`, the tokens controller and the schema.

## Decisions

| ID | Decision | Status | Evidence | Recommendation |
| --- | --- | --- | --- | --- |
| D1 | Parent identity / T1 | supported | E2 | `guardianships(user_id, family_id)`, unique per user for now; a user with no memberships has no centers, so every director endpoint is a 404 |
| D2 | Family scoping / T1 | supported | E2 | `Api::V1::Parent::*` start from `Current.user.families`; `evals/latest` needs a center; a per-user rate limit on family endpoints |
| D3 | Delivery / T1 | supported | E2 | `approve!` writes a `FamilyMessage` in the approval's transaction (unique per action) with a fixed subject, because directors review only the body; approving a family-facing action with no text fails |
| D4 | App auth / T1 | supported | E2 | `POST /api/v1/tokens`; the token goes in the Keychain with `AfterFirstUnlockThisDeviceOnly`; sign out revokes it; a 401 ends the session; director accounts are refused and their token revoked |
| D5 | Information architecture / T3 | supported | E1 | Three tabs: Today (check-in state now, two weeks of attendance, in the center's time zone), Messages (unread state, read on open), Billing (due first, with a total) |
| D6 | Toolchain / T3 | supported | E3 | XcodeGen `project.yml` checked in, project generated; Swift Testing for the client, XCUITest for the flow with screenshots |

## Limits

- One family per parent account until the family endpoints take a family id.
- Messages are in-app only; nothing is emailed or pushed.
- Independent security review of `3fd8a7c` (2026-10-19): no HIGH. Fixed in `2ed83c9`:
  - fixed subjects
  - one family per user
  - `evals/latest` for directors only
  - malformed `days`
  - a per-child query
  - a family rate limit
- Review triggers: push notifications, parents with several families, parent replies, or payments.
