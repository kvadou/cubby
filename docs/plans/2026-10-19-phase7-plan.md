# Phase 7 plan: iOS parent app

Decisions and evidence: [`docs/prior-art/2026-10-19-phase7-ios.md`](../prior-art/2026-10-19-phase7-ios.md).

## Done when
A parent signs in to a SwiftUI app in the simulator against the local API and sees three tabs:
- **Today:** each child's check-in and check-out, plus the last two weeks of attendance.
- **Messages:** what the center sent.
- **Billing:** invoices, with past-due ones first.

When a director approves a family-facing message in the web app, it appears in that parent's Messages tab. A parent can never see another family's data or any director endpoint. API request specs prove the isolation; Swift tests cover decoding and the client; a UI test signs in, walks the tabs, and saves screenshots.

## API

| Method | Path | Returns |
| --- | --- | --- |
| GET | `/api/v1/me` | Adds `families: [{id, name, center_name}]` |
| GET | `/api/v1/family` | Family, center, children with classroom and today's attendance, unread count |
| GET | `/api/v1/family/children/:id/attendance?days=14` | Days with check-in and check-out |
| GET | `/api/v1/family/messages` | Newest first |
| POST | `/api/v1/family/messages/:id/read` | Marks read (idempotent) |
| GET | `/api/v1/family/invoices` | Open and past due first, then paid |

Scoping: every family endpoint starts from `Current.user.families`, the same way director endpoints start from `Current.user.centers`. A parent has no centers, so every director endpoint is a 404. Mobile signs in with the existing `POST /api/v1/tokens`, a bearer token that is exempt from the CSRF check.

## Schema

```ruby
create_table :guardianships do |t|
  t.references :user, null: false, foreign_key: true
  t.references :family, null: false, foreign_key: true
  t.timestamps
  t.index %i[user_id family_id], unique: true
end

create_table :family_messages do |t|
  t.references :family, null: false, foreign_key: true
  t.references :center, null: false, foreign_key: true
  t.references :proposed_action, foreign_key: true, index: { unique: true } # null for announcements
  t.string :subject, null: false
  t.text :body, null: false
  t.datetime :sent_at, null: false
  t.datetime :read_at
  t.timestamps
end
```

## Delivery

```ruby
def approve!(by:, final_body: nil, now: Time.current)
  self.class.transaction do
    transition!(...)                      # unchanged
    deliver_to_family!(now) if family_facing?
  end
end
```

The family comes from the subject: a `Family` for past-due tuition, or `Enrollment -> child -> family` for the waitlist. The message is written in the same transaction as the approval, so an approved message is never lost.

## iOS (`ios/`)
- **Project:** SwiftUI, iOS 18+, generated from a checked-in `project.yml` by XcodeGen. Swift 6 strict concurrency.
- **Code:**
  - `APIClient`: an actor using async/await URLSession with Codable and ISO 8601 dates.
  - `Session`: the bearer token in the Keychain (this device only, after first unlock).
  - The base URL comes from the scheme: localhost for the simulator, or the CloudFront URL.
- **Screens:** sign in, the Today, Messages and Billing tabs, and sign out (revokes the token).
- **States:** loading, empty, error and offline are designed, not left blank. Dynamic Type, VoiceOver labels, and light and dark mode.
- **Tests:** a Swift Testing unit target (decoding, client against a stubbed URLProtocol) and an XCUITest target that signs in with the local seed values and attaches screenshots.

## Steps
1. Migrations, models, delivery on approve, family endpoints, `me` families, seeds (a demo parent for a Little Oaks family with an enrolled child and a past-due invoice, plus one welcome message).
2. Request specs for isolation (parent vs another family, parent vs director endpoints, director vs family endpoints), delivery, and read state; tier-1 review.
3. The web app tells a parent who signs in there to use the mobile app.
4. iOS app, tests, simulator screenshots at a standard and a large text size.
