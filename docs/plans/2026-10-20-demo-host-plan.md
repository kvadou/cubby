# Always-on demo host and Android app (2026-10-20)

## Ask

Make the deployed site something anyone can try without Docker on Doug's Mac or a $5-a-day cluster; decide between a login and a demo; show the iOS and Android apps as screenshots.

## Decisions (Doug, 2026-10-20)

- **D1 Hosting: one small server, not EKS full time.** EKS's control plane alone is about $73 a month, over the $50 budget. A t4g.small (about $12) plus a 20 GB disk and a public IPv4 address comes to about $18 a month. The EKS stack stays available through `make up` / `make down`, and CloudFront prefers it while it's up (`bin/api-origin`).
- **D2 One-click demo, not a printed password.** `POST /api/v1/demo_session` starts a cookie session as the demo director, only where `Demo.enabled?` (development, or `CUBBY_DEMO=1`). The typed password still works.
- **D3 Build the Android app (Phase 8) before taking screenshots,** rather than mocking them. Installs: Homebrew `openjdk@21` and `android-commandlinetools` (not Android Studio), SDK platform 37, build tools 37, an Android 16 emulator image.

## Demo host design

- **Network:** VPC 10.50.0.0/16, one subnet in use1-az1 (CloudFront VPC origins don't support use1-az3). The instance has a public IP for outbound only (ECR, GitHub, AWS APIs), so no NAT gateway is needed. Port 80 admits only `CloudFront-VPCOrigins-Service-SG`, which CloudFront creates for this account's VPC origin. That is tighter than the managed prefix list, which any CloudFront distribution could use against the public address.
- **Process model:** Docker Compose. `prepare` (migrate, seed, scan) must finish before api, sidekiq and events start, mirroring the EKS init container.
- **Delivery:** `deploy.sh` runs on a systemd timer every 5 minutes. It reads `newTag` from `deploy/production/kustomization.yaml` on main, accepts only 40 hex characters, and pulls from this account's immutable ECR repository.
- **Secrets:** generated by Terraform, stored as SSM SecureStrings, read at boot into 0600 env files. No xtrace in the boot script.
- **Self-healing:** a CloudWatch alarm recovers the instance on a system check failure and reboots it on an instance check failure; both alarms notify the alerts topic.

## Security review (independent, before the first apply)

No HIGH findings. Fixed before shipping:

- **M1:** xtrace would have written secrets to the boot log. Removed it, and the presence check no longer expands the values.
- **M2:**
  - Postgres and Valkey now run on an internal-only Docker network, so they can't reach instance metadata.
  - Third-party images are pinned by digest.
  - Bedrock is narrowed to the two models and the embedding model the app uses.
  - The managed SSM policy is replaced by the Session Manager subset, without account-wide `ssm:GetParameter`.
- **M3:** `Demo::Reset` refuses any database that has a user whose address isn't `.test`, regardless of configuration.
- **M4:**
  - Ask Cubby is now limited per session and per address, ahead of the shared-account ceilings.
  - Visitor-written text stays visible to other visitors until the nightly reset. Accepted for a fictional demo.
- **L1:** IPv6 viewers are rate-limited per /64.
- **L2:** Valkey's memory ceiling is raised to 384 MB.
- **L3:** a spec asserts that session ids keep increasing across a reset, because cookies hold the id.

## Verification

- API: 203 specs, rubocop and brakeman clean. The production image runs under the host compose file locally: healthy, demo endpoint 201, two resets in a row, about 420 MB in total. The data network has no egress; the app network does.
- Web: a click-through at 390 px goes from "Try the demo" to the inbox. The `/apps` page has no page-level horizontal scroll.
- iOS and Android: the UI flow tests sign in, walk every tab and sign out. A director approval made through the model appears unread in both apps, and those screenshots are on `/apps`.
